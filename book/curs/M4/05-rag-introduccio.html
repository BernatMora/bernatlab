📖 Resum del capitol

La idea clau

RAG vol dir Retrieval Augmented Generation (Generacio augmentada per recuperacio). Es la tecnica que permet a un LLM respondre sobre les teves dades, no nomes sobre el que va aprendre durant l'entrenament. En lloc d'entrenar un model nou (car i complicat), li dones el contexte relevant a cada pregunta. I el millor: funciona amb qualsevol LLM.

El problema que resol

Si vols preguntar al teu LLM local: "Com es configura el sensor d'humitat del Hort Osona?", el model llama3.2:3b no te ni idea. Et respondra amb bestieses o et dira que no ho sap.

Tres possibles solucions:

  1. Re-entrenar el model amb les teves dades. Car, lent, nomes per a tu.
  2. Fine-tuning: re-entrenar nomes una mica. Millor pero encara complicat.
  3. RAG: donar-li el contexte adequat. Rapid, barat, funciona.

RAG es, amb diferència, la mes practica.

Com funciona RAG (visio general)

El flux te tres fases:

1. INDEXACIO (es fa un sol cop)
   Documents -> Chunks -> Embeddings -> Vector DB

2. QUERY (cada vegada que l usuari pregunta)
   Pregunta -> Embedding -> Cerca a Vector DB -> Top-K chunks

3. GENERACIO (L hora de la veritat)
   Pregunta + Chunks rellevants -> LLM -> Resposta

Exemple: vols preguntar "Quin sensor mesura la temperatura del sol?". Calculem l'embedding de la pregunta, busquem els 3 chunks mes semblants a ChromaDB, i els enviem al LLM juntament amb la pregunta.

Per que es tant poderós?

  • Sempre actualitzat: nomes cal re-indexar.
  • Font verificable: podem citar el document origen.
  • Privadesa: les dades mai surten del sistema.
  • Multi-document: milers de documents, el model veu nomes els rellevants.
  • Barat: nomes electricitat per consulta.
  • Funciona amb models petits: un 3B amb bon RAG pot superar un 70B sense RAG.

Les limitacions

  • Qualitat del retrieval: si no trobem els chunks correctes, el LLM falla.
  • Finestra de context: nomes 4-10 chunks per consulta.
  • Chunking dolent: perdem contexte si partim malament.
  • Manteniment: cal re-indexar quan canvien els documents.
  • Cost de calcul: generar embeddings costa temps.

Components d'un sistema RAG

  1. Loader: carrega els documents (PDF, Markdown, HTML).
  2. Splitter: parteix els documents en chunks (100-1000 tokens).
  3. Embedder: converteix cada chunk en un vector numeric.
  4. Retriever: busca els chunks mes semblants.
  5. Generator: el LLM que genera la resposta final.
  6. Vector DB: on es guarden els embeddings (ChromaDB, FAISS, LanceDB).

Regla practica: comença sempre per prompt engineering. Si no n'hi ha prou, afegeix RAG. Si encara no es suficient, considera fine-tuning.

Un exemple real al BernatLab

Un assistent per l'Hort Osona:

  1. Reuneixo els documents (articles, logs, manuals).
  2. Els indexo amb un script Python.
  3. Munto una API que, donada una pregunta, busca els chunks i els envia a Ollama.
  4. L'usuari pregunta: "Quan he de regar els tomàquets al març?"
  5. El sistema respon citant fonts.

Tot en un dia de feina. I el resultat es un assistent que sembla que "sap" tot sobre el teu hort, quan en realitat nomes te una base de dades i un LLM de 3B parametres.

Errors comuns amb RAG

  • Chunks massa grans: no caben al contexte.
  • Chunks massa petits: perden el significat.
  • Embedding equivocat: no tots serveixen per a tot.
  • No netejar el text: caracters extranys perjudiquen la cerca.
  • No re-indexar: la base queda obsoleta.
  • Massa chunks al prompt: enviar 20 chunks l'enreda.

🛠️ Exercici practic (30-45 min)

Entendre el flux de RAG a ma: partir un document en chunks, calcular embeddings, i fer una cerca per semblança.

Pas 1: Prepara l'entorn (5 min)

mkdir -p ~/bernatlab-exercicis/M4/05-rag
cd ~/bernatlab-exercicis/M4/05-rag
python3 -m venv venv
source venv/bin/activate
pip install ollama numpy

Pas 2: Crea un document de prova (5 min)

cat > hort_osona.md << 'EOF'
# Hort Osona - Manual de cultiu

## Tomàquets
Necessiten sol directe (6-8 hores) i reg regular. Plantar a la primavera.

## Enciams
Prefereixen temperatures fresques (15-20 graus). Reg diari pero sense entollar.

## Sensors
- DS18B20: temperatura del sol
- DHT22: humitat i temperatura ambient
- Capacitive Soil Moisture: humitat del terra
- BME280: pressio atmosferica

## Reg automatic
S'activa quan la humitat del terra baixa del 30%.
EOF

Pas 3: Partim el document en chunks (10 min)

Crea chunks.py amb una funcio chunk_by_section que parteix per seccions (##). Hauries d'obtenir 4 chunks.

Pas 4: Calcular embeddings amb Ollama (10 min)

ollama pull nomic-embed-text

Crea embeddings.py amb un bucle que calcula l'embedding de cada chunk amb ollama.embeddings.

Pas 5: Fer una cerca per semblança (10 min)

Crea cerca.py amb funcio cosine_similarity. Fes la pregunta "Quin sensor faig servir per saber la temperatura del sol?" i veuras com el chunk "Sensors" surt en primer lloc.

Pas 6: Munta el prompt final (5 min)

Crea prompt_final.py que construeix el prompt amb contexte i crida Ollama amb ollama.chat. Aquest es el RAG complet!

Validacio

  • ☐ Has preparat l'entorn amb venv.
  • ☐ Has partit el document en chunks.
  • ☐ Has calculat els embeddings.
  • ☐ Has fet una cerca per semblança.
  • ☐ Has completat el prompt RAG i el LLM ha respost correctament.

✅ Respostes

Les respostes completes amb explicacions estan al fitxer respostes.md del repositori.

Resum rapid

  1. RAG = Retrieval Augmented Generation.
  2. Problema = respondre sobre dades noves.
  3. 3 fases = indexacio, query, generacio.
  4. Chunk = fragment de text d'un document.
  5. Recomanacio = 3-5 chunks per consulta.
  6. No es RAG = compilador de Python.
  7. Embedding = vector numeric que representa significat.
  8. Regla = prompt engineering -> RAG -> fine-tuning.
